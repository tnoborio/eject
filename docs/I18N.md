# Internationalization

[日本語](I18N.ja.md)

EJECT is international by design. The product's primary event—a person presses
a button and another person's tray moves—should cross language boundaries with
very little explanation.

## Initial locales

- `en`: canonical product copy and canonical repository documentation;
- `ja`: first complete translation.

English being canonical is a maintenance decision, not a claim that English is
the default for every user. The client initially selects a locale from the
browser or operating system, then persists the user's explicit choice.

## Product name

`EJECT` and the ⏏ symbol do not change by locale. Surrounding descriptions,
controls, notifications, errors, dates, and accessibility labels are localized.

Do not use flags to represent languages.

## Protocol rule

The server returns semantic codes and structured variables, never a prewritten
English or Japanese sentence.

```json
{
  "event": "PERSON_EJECTED_YOU",
  "variables": {
    "actorDisplayName": "Kaz"
  }
}
```

Clients render the event in the recipient's locale.

```text
en: Kaz ejected you.
ja: Kazがあなたをejectしました。
```

## Message format

- Use an ICU MessageFormat-compatible system.
- Support plural rules even if early messages rarely need them.
- Use locale-aware date, time, number, and relative-time formatting.
- Never build sentences by concatenating translated fragments.
- Keep variables semantic and escaped; never inject markup from display names.
- Give translators context, screenshots where useful, and a description of each
  variable.
- Test longer strings and scripts with different text metrics.

## Illustrative message keys

```text
action.eject
action.ejectBack
event.personEjectedYou
event.trayOpened
event.commandDelivered
status.available
status.paused
status.offline
status.cooldown
error.driveBusy
error.driveUnsupported
error.resultUnknown
permission.allowPerson
permission.revokePerson
```

Keys describe meaning, not English wording. Do not create keys such as
`kazEjectedYouText` or `greenButtonLabel`.

## Layout and accessibility

- Do not embed words in bitmap assets.
- Let controls expand instead of assuming English button widths.
- Provide localized accessible names for ⏏ and other icons.
- Preserve keyboard navigation and visible focus.
- Do not rely on color alone for delivery or failure states.
- Keep user display names in Unicode and handle bidirectional text safely.
- Design for locale expansion and future right-to-left support even if RTL is
  not an initial launch locale.

## Locale ownership

Locale belongs to the person for web experiences and to the local application
for native notifications before sign-in. A server-side account preference may
synchronize the choice, but a sender never selects the recipient's notification
language.

## Documentation policy

Every canonical product document has a paired `.ja.md` translation. Changes to
meaning should update both in one change. Each file links to its counterpart.

Machine translation may assist drafts, but product terminology, security
meaning, and consent language require human review before release.

## Adding another locale

Before marking a locale supported:

1. translate every required message, notification, onboarding step, permission,
   error, privacy statement, and safety warning;
2. review the glossary and the product-specific use of “eject”;
3. run missing-key, variable-parity, and formatting checks;
4. visually test web and desktop surfaces;
5. test locale selection, fallback, dates, names, and accessibility labels;
6. assign a maintainer or review path for future updates.

Partial translations may be offered only when clearly labeled experimental and
when consent and security text still has an approved fallback.
