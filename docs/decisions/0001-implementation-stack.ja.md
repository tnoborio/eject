# ADR 0001: 初期実装スタック

[English](0001-implementation-stack.md)

- **状態:** 採用
- **日付:** 2026-07-18

## 背景

EJECTは最初にWindows上の物理的なトレイ動作を検証し、その後、デスクトップ
エージェントをリモート管理へ広げることなく2人を接続する必要があります。リポジトリ
には当初、プロダクトとアーキテクチャの文書だけがあり、実装はありませんでした。
現在のビルドホストはLinux ARM64で、現時点ではWindowsテスト端末がありません。

## 決定

1. Stage 0のWindowsスパイクをC#と.NET 10のコンソールプログラムとして実装する。
2. Linux上で未署名かつ自己完結型の`win-x64`実行ファイルをクロス発行する。
3. 実際のWindowsハードウェアで物理動作を検証するまで、WinUI 3とMSIXパッケージを
   延期する。
4. Stage 1ではWebクライアントとモジュール化した制御面にTypeScriptとNext.jsを使い、
   Vercelへ配置する。
5. Managed PostgreSQLと人向けのManaged認証を使い、当初はSupabaseを優先候補とする。
   デバイス資格情報は人のセッションから分離する。
6. デバイス配送は認証済みのアウトバウンドHTTPSポーリングから始める。リアルタイム
   プロバイダーはコマンドの正本ではなく、交換可能な起床通知用トランスポートとする。
7. OpenAPIまたはJSON Schemaで共有意味契約を定義し、ユーザー向けメッセージはすべて
   英語と日本語のロケールリソースに置く。

## 影響

- Linux上でStage 0コードの大部分をコンパイルおよびテストできるが、物理的な能力契約、
  Windows権限、ハードウェア挙動は確定できない。
- 最初の実行ファイルにはネットワーク機能がなく、任意のデバイスパスやIO制御コードを
  受け取らない。
- Stage 0にVercelは不要であり、サーバー実装をハードウェア上の事実より先行させない。
- 制御面はモジュラーモノリスとして始める。認可やライフサイクルの意味を変えずに、
  コマンドトランスポートを別サービスへ移動できる。
- Stage 1のアカウント登録とデバイス登録を完成させる前に、認証プロバイダーと具体的な
  暗号方式について集中的なセキュリティ判断が必要になる。
