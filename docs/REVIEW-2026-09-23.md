## Findings

1. **High, before delivery: eject-back authorization has no time limit.**
   `control-plane/src/modules/eject/infrastructure/postgres-issuance-store.ts:167`
   checks source participants, source status, and previous consumption, but not
   elapsed time. An old `OUTCOME_UNKNOWN` or `FAILED` command remains a source
   indefinitely. Eject back bypasses the ordinary directional-grant test, so
   this contradicts ADR 0003's short-lived consent. Define a separate reply
   deadline and check it transactionally, with expiry-boundary tests. This is
   currently latent because no person-facing issuance route exists.

2. **High, before delivery: late results can be permanently rejected.**
   `control-plane/src/modules/eject/infrastructure/postgres-agent-transport-store.ts:185`
   accepts a first result only while the command is `DISPATCHED`. A recipient
   pause or grant revocation cancels dispatched commands even when the device
   has already attempted the action and its result is delayed. A subsequent
   poll can similarly expire a dispatched command. The later authenticated
   result then receives `COMMAND_MISMATCH`, losing the execution evidence.
   Distinguish stopping further delivery from evidence of an earlier attempt;
   retain late observations without authorizing another action or weakening
   revoked-key rejection. Test poll/attempt/pause/result and delayed-result
   orderings against PostgreSQL. This finding is from code-path analysis, not
   a newly executed database race test.

3. **Medium, current web flow: one incorrect OTP prevents an ordinary retry.**
   `control-plane/src/modules/identity/transport/person-auth-http-handlers.ts:120`
   clears both challenge cookies on rejection or provider unavailability, while
   the same handler requires them and the UI leaves the OTP form open. A
   bounded local handler reproduction with synthetic input returned 401 on
   the first rejected OTP, cleared both cookies, then returned 400 without
   calling the provider on retry. Preserve the bounded challenge for permitted
   retries, or explicitly reset the UI and require a new code; retain provider
   attempt limits. Add an incorrect-then-correct OTP flow test.

4. **Medium, current web flow: session refresh is not connected to the UI.**
   `control-plane/src/app/web-console.tsx:115` treats 401 as signed out. No
   browser caller invokes the implemented `/api/person/v1/auth/refresh` route.
   After access-token expiry, a valid refresh cookie cannot restore the session
   through normal interaction. Add a single coordinated refresh and bounded
   retry, with explicit handling for expired refresh credentials and multiple
   simultaneous requests. Test expiry during pause/revoke operations.

## Missing MVP connections, not regressions

- Enrollment inserts `SETUP_IN_PROGRESS`, `OFFLINE`, and no approved drive.
  Poll authentication requires `READY`; no production path promotes the
  device after local approval/setup testing. Define a narrowly authorized
  readiness report and current availability expiry, without presence history.
  Participation readiness and availability must also reach the default sender
  eligibility rules.
- There is no person-facing issuance route, result-status route, recipient
  EJECT interaction, or complete Windows network client. The CLI only lists
  and locally ejects. Durable command consumption, crash handling, stored-result
  resend, local pause, notification, and protected enrollment wiring remain.
- Quiet hours are hard-coded to false in the PostgreSQL authorization mapper.
  Hourly limits exist, but daily-limit enforcement is absent. Do not advertise
  these controls as working; complete the intended safety policy before alpha.
- Selected recipient limits default to zero, and missing entitlements yield
  zero. Delivery gates and working hardware alone will therefore not permit
  issuance. A reviewed test-participant setup must establish explicit safe
  limits and a free pilot entitlement without weakening fail-closed defaults.
- Drive IDs hash a drive letter rather than a stable hardware binding. Before
  remote use, invalidate approval when identity cannot be established after a
  reconnect; do not silently approve a different drive at the same letter.
- Browser flow tests are absent. The 100% coverage requirement applies to a
  selected set of modules, not the whole product or browser/Windows integration.
- Invitation cleanup needs scheduling. Broader event retention, deletion,
  emergency operating procedures, signing/update distribution, and independent
  security review remain alpha work, not completed capabilities.

## Recommended MVP boundary and order

Keep invited participants, one Windows device and one approved tray drive per
person, named directional grants, pause/revoke, a conservative cooldown and
limits, truthful outcomes, notification, and one bounded eject back. Defer
billing, broader audiences, multiple devices, macOS, feeds, and other outputs.
Existing future-facing policy code need not be removed; do not expand its UI
or add billing integration during this validation.

1. Repair OTP retry and refresh, then verify the two-account browser consent
   flow and schedule invitation cleanup.
2. Resolve reply expiry and late-result semantics; add targeted regression
   tests before enabling any remote action.
3. Run the Windows hardware kit in parallel. Confirm a narrow supported drive
   contract, standard-user operation, and protected-key behavior.
4. Complete readiness/availability and the end-to-end Windows delivery slice,
   including durable replay prevention and local pause. Keep gates disabled
   until their existing evidence requirements are met.
5. Complete a two-person physical call-and-response. Record setup friction,
   failures, understandable status, and whether participants voluntarily want
   to repeat it. Use participant feedback, not reaction surveillance. Only then
   expand to a small private alpha with distribution and operational controls.
